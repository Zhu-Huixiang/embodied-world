# 全身动作写成208个token，机器人就懂了吗？

![AI 生成封面；概念插画，不是论文实机实验画面。](cover.png)


设想一个人形机器人要去桌边拿杯子。手伸到了，脚却没跟上；身体再往前倾一点，抓取就变成了失衡。

对机械臂来说，动作可以是手腕位置加一个夹爪开合。换成全身，腿、腰、双臂和手指都要参与。这里多出来的，既是维度，也是彼此牵制的关系。

地平线的 Holo-M 把问题推向了一个有争议的选择：**语言模型看懂任务之后，动作还要不要交给另一个模型？**

它在挑战的，是 π0、Ψ0 等路线里的分工：视觉语言模型提供上下文，另一个连续动作专家负责生成轨迹。Holo-M 想让动作进入语言模型自己的词表，用同一个序列模型输出全身动作。作者认为，这能避开独立动作专家与语言骨干之间的知识隔离问题。<!-- evidence:C01 -->

这个愿望并不难理解。难的是下一步：你给机器人增加了一门“动作语言”，它会不会还在组织词句，杯子已经被碰倒了？

带着三个问题往下读：

1. **全身动作为什么要进入语言模型的词表？**
2. **人类视频没有机器人的腿部标签，怎么一起训练？**
3. **208个动作token，怎样赶上机器人的控制时钟？**

## 先把“懂了”和“做了”之间的接口找出来

连续动作专家的价值很实在：它擅长输出数值轨迹。一个预训练语言模型，未必天然擅长回答“接下来手腕移动几厘米”。让两个模块各做所长，是合理的设计。

Holo-M 换了一个接口。输入图像、任务指令、机器人设置与状态之后，Qwen3-VL-2B 直接预测扩展词表里的动作 token；再把 token 解回连续目标，交给全身控制器 WBC。图里最该看的，是 VLM 到动作生成这一段，以及底部仍然存在的控制器。<!-- evidence:C02 -->

![Holo-M 原始架构：统一动作表示、分组解码与全身控制器](figures/original/fig1-original.png)

论文原图 · Fig. 1 · PDF 第 3 页 · arXiv v1。注意底部的 Whole-Body Controller：语言模型没有独自接管平衡与所有电机控制。

所以，“全身动作为什么要进入语言模型的词表？”的答案首先是一种建模选择：**动作成为这个序列模型直接学习的输出，而非另一个连续专家的输出。**

这还不能推出“机器人继承了语言模型的全部推理能力”。v1 没有展示交错生成推理文本与动作的实验，也没有专门测量视觉语言知识保留。作者在结尾提出的推理扩展，仍是未来方向。<!-- evidence:C03 -->

接口接通了，只完成了第一步。接下来要解决一个更朴素的问题：人的动作和机器人的动作，究竟有没有共同的写法？

## 人类的手，能教会机器人的腿什么？

看第一视角视频，能估计人的手腕和指尖怎样移动。但你不能凭空补出：同一时刻，G1 的哪个腿部关节应该转多少度。

如果要求每份数据都带着完整全身标签，大量人类操作数据就会被挡在训练集外。

Holo-M 把动作拆成四组。这里是表示的四个部分，包含任务空间与关节空间的重叠描述，**96 维并不等于机器人有 96 个电机**。<!-- evidence:C04 -->

| 动作组 | 表示 / token数 |
| --- | --- |
| EEF | 手腕、指尖位姿 / 100 |
| Body | 身体关节目标 / 62 |
| Hand | 手部关节目标 / 32 |
| Kinematics | 底座运动指令 / 14 |

EEF 提供共享的任务空间表征，论文将它用于训练中的跨数据对齐。人的手和机器人的手都能描述成“朝什么位置、什么姿态移动”，不必先拥有同一套关节结构。

这就是“人类视频没有机器人的腿部标签，怎么一起训练？”的回答：**只对这份样本实际拥有的组计算损失。** EgoDex 的人类样本只监督 EEF，缺失的 Body、Hand、Kinematics 不填假目标，也不参与损失。机器人数据再提供本体与控制相关的监督。<!-- evidence:C05 -->

“共享”在这里有一个明确边界。人类视频增加的是可用监督，并没有直接提供机器人腿部真值；这套表示也没有消除硬件对应关系，身体和手的关节顺序依然与本体有关。

先混合 EgoDex 与 Humanoid Everyday 做自回归预训练，再用 SIMPLE 做人形任务对齐，之后改为分组去 mask 的训练方式；若需要单任务 specialist，最后才做对应任务适配。同一骨干与词表贯穿这些阶段，视觉编码器冻结，语言骨干继续优化。<!-- evidence:C06 -->

这套办法有没有实际帮忙？论文有一组比总榜更值得看的数据。

## 我更想看的是：把数据拿掉，成绩会怎样？

Table 5 保持 Qwen3-VL 骨干与动作组顺序不变，考察 Holo-M AR 的预训练数据来源。在 SIMPLE 闭环评估中，每种设置都是六个任务、三个随机化等级、每格十次，共 180 次。<!-- evidence:C07 -->

| 预训练来源 | 成功次数 |
| --- | --- |
| 无动作预训练 | 53/180 |
| Humanoid Everyday | 119/180 |
| EgoDex + Humanoid Everyday | 138/180 |

“无动作预训练”仍从预训练 VLM 开始，并非整个模型从零训练。

先加入人形机器人数据，多了 66 次成功；再加入人类 EgoDex，多了 19 次。它支持了一个较窄、也较有用的判断：在这套训练流程与基准里，不完整的人类监督确实能够补充机器人数据。

但这组消融并没有单独拿掉 EEF 共享组，也没有用另一种 tokenizer 配同样的数据重跑。它不能把全部收益都归给“四组 token”这一项设计。**数据有用，表示有用，二者各占多少，仍需要更细的实验。**

现在，还有第三个问题没过关。数据可以慢慢收，机器人执行时却等不了。

## 208个token，不必一个个等它说完

Holo-M 处理的是一秒动作块：30 Hz 下的 30 个时间步。每组先用 DCT 保留每个维度的两个低频系数，再用四级残差向量量化 RVQ 编码剩余误差。这样得到固定长度的四组 token，总计 208 个，不包含组边界等结构 token。<!-- evidence:C08 -->

可以把它理解成：先写出轨迹的低频部分，再编码需要补回的残差。残差不能省掉，否则动作里的变化也可能跟着被抹平。

固定长度还有一个工程用途：每组的位置和边界明确，方便同时恢复被遮住的 token。

它的离散扩散是对 token 去 mask。当前组里的位置并行预测，置信度较高的位置先确定；这一组完成后，下一组再读取前面的结果。因此，**组内并行，组间仍按 EEF、Body、Hand、Kinematics 的顺序生成**。前缀和已完成组会缓存。<!-- evidence:C09 -->

![Holo-M 中文机制图：缺失组监督、固定长度 token、分组解码与控制时钟](figures/drawpaper/holo-m-method-v2.png)

AI 生成示意图，使用 DrawPaper skill 绘制；经原文核对，不是论文实验图。插画来自内置生图草稿，文字、公式与计算连线经 TikZ 精排；图中的同时执行/推理为概念时序。

每组八轮、四组共 32 次顺序解码步骤，相比逐 token 自回归的 208 次，顺序深度缩短了 6.5 倍。**这是解码深度的比值，不能直接写成实机推理快了 6.5 倍。** 并行计算的每一步也有成本。<!-- evidence:C10 -->

这种折中没有让四组完全独立。代价是后面的组仍要等前面的组；价值是后面的动作可以参考已经生成的前部结果。这个固定顺序是否最优，v1 没有给出组顺序消融。

## 快一点之后，任务到底好了多少？

先看 generalist：一个 checkpoint 在 SIMPLE 的 24 个任务上联合训练，再评估其中六个代表任务，不做逐任务适配。三种随机化等级各十次，仍是每个方法 180 次。<!-- evidence:C11 -->

| Generalist 方法 | 成功次数 |
| --- | --- |
| Ψ0 | 114/180（63.3%） |
| Holo-M AR | 138/180（76.7%） |
| Holo-M | 143/180（79.4%） |

从 AR 到分组离散扩散，多成功五次。更大的总分差距，在 AR 版本里已经存在；从这个结果看，不能把 Holo-M 的优势全归给扩散解码。

对照也有条件：论文说各方法使用相同的适配数据，但 Ψ0、π0.5 只微调动作头，DreamZero 用 LoRA，Holo-M 则优化语言骨干；初始化模型也不同。这是所报告训练配置的比较，未控制每条路线所有可能的训练选择。<!-- evidence:C12 -->

总分还藏着局部退步。XMovePick 的 Level 2，Holo-M 是 3/10，AR 是 8/10，Ψ0 是 9/10。每格只有十次，不宜据此给一个机制定罪；但它足以提醒我们，**总分更高，不等于每一种场景更稳。**<!-- evidence:C13 -->

单任务 specialist 又是另一笔账：Holo-M 163/180，Ψ0 154/180；该表的基线数值来自 SIMPLE 原有报告。它不能与上面的单 checkpoint generalist 混成一个“90.6% 的全能模型”。<!-- evidence:C14 -->

## 真正紧张的地方，是下一段动作接管前

“208个动作token，怎样赶上机器人的控制时钟？”还需要执行系统来回答。

实机用 G1-comp、两只 Dex3 手和头部 RealSense 相机，模型跑在单张 RTX 5090 上。每次预测一秒动作，但每 500 ms 就采一份新观测：推理下一块时，机器人继续执行上一块。<!-- evidence:C15 -->

先看原图里的两条动作块。它们覆盖的预测时间有重叠；并不是每个新块都从自己的第一个动作开始执行。

![Holo-M 原始实机部署时序：推理与上一动作块执行交叠](figures/original/fig3-original.png)

论文原图 · Fig. 3 · PDF 第 10 页 · arXiv v1。横轴是控制 tick；新观测到来后仍有推理等待，不能把图里的 500 ms 当作每个电机的控制周期。

把接管的那一段放大来看：

![Fig. 3 原图局部：旧块先执行，下一块从第15步接管](figures/original/fig3-takeover-original-detail.png)

论文原图局部 · Fig. 3 · PDF 第 10 页 · arXiv v1；仅裁切放大，未重绘。从上到下是旧块 k、新块 k+1、实际发送的动作。紫色是等待期间未使用的新块前段，蓝色是发出的动作；0.5 s 处，新块从标为 15 的位置接管。

后续新块会丢弃 hold 等待期间对应的前段预测，从等待结束处接管。八轮去 mask 时，每个 30 步动作块的推理延迟为 **476.8 ± 16.9 ms**，固定 hold 预算为 **500 ms**。二轮、四轮的均值分别是 175.8、275.7 ms，但论文没有给出这些步数各自对应的实机任务成功率。<!-- evidence:C16 -->

“能装进时间窗”与“总能及时纠偏”之间，仍有距离。这个均值已经靠近预算边界，文中没有给出长尾延迟或超预算频率。减少轮数可以省时间，是否会损害动作质量，需要另测。

实机证据也应按原来的大小看：两项任务都使用在部署场景采集的各 100 条遥操作数据做 specialist 适配，再各试十次。Tabletop Grasp 为 10/10，Move Pick 为 8/10。它说明系统能在这些场景运行；还没有回答换场景、突发扰动和长期运行会怎样。<!-- evidence:C17 -->

## 回到这三个问题，剩下哪一问最值得追？

第一个问题，动作进入词表，改变了视觉语言模型与动作输出的接口。它让同一个序列模型直接学动作；语言推理是否随之可靠地迁移到了控制，还没有被 v1 证明。

第二个问题，缺失的标签可以不参与损失，人类的 EEF 监督于是有了入口。数据消融给出了支持；共享表示与数据规模各自的贡献，尚未拆清。

第三个问题，208 个 token 通过组内并行去 mask 缩短顺序深度，再借助动作块重叠执行赶上固定时钟。控制器和调度承担了落地的一部分工作，模型分数无法替它们交卷。

我更想追问的是：**如果场景在动作块中途变了，这套“更快地生成整块动作”能否真的更快纠正？**

一个可检验的实验，是固定 checkpoint、动作块长度与控制器，只改去 mask 轮数和观测更新间隔；分别记录任务成功率、扰动后的纠偏时间与超预算次数。这样才知道，省下来的计算究竟变成了反应能力，还是只让原来的动作更快进入队列。

Holo-M 给出了一条值得继续读的路线。下一份证据，我想看它如何处理动作被现实打断的那一刻。
